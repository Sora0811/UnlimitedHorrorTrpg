## 1. 這個 repo 是什麼

Unlimited Horror TRPG 2.34 正式版規則書，原為 CHM 格式。目前已完成：CHM 解包、UTF-8 轉碼、簡轉繁、**規則／資源結構拆分**、**每條目一資料夾重整**、**導航依原始編排排序**、**清除空佔位頁**、入口網站。

**規則書內容尚未轉換成任何結構化資料**（`rules.yaml` 之類），這是後續 App 開發的前置工作。

**資源抽取已達「可作為資料來源」的階段**【觀察】：`build/extract_batch.py` 能把 1146 個條目頁全部分段抽完並合併（§7.4），抽取器的三個系統性缺口已於 2026-10-22 修好並通過回歸測試（§7.6）。欄位保留率 100%、價格解析率 98.8%。條目名稱的散文誤判已於同日修正（§7.8），完全沒內容的條目降為 0。

**資源區已有可讀的 Markdown 版本**【觀察】：`build/export_md.py` 把抽取結果轉成 1019 頁 Markdown（§7.8），可用 `python build/export_md.py` 重建。**規則區尚未轉換**——規則頁是散文體，需要另外的抽取邏輯。

### 每條目一個資料夾【決定】

**結構 = 完整分類路徑 + 條目資料夾，內容一律命名為 `index.html`。**

```
Resource/資源/血統/人類/特異本質/禍神血脈/index.html
Resource/資源/物品/科技本質/D級系列武器/D級手槍系列/index.html
Resource/規則/ST幫助/巨龍/index.html
```

這個設計的目的是**支撐分支與補丁**：一個條目的所有版本與附屬資料放同一個資料夾。

```
Resource/資源/血統/人類/特異本質/禍神血脈/
├─ index.html              現行版本（2.34）
├─ patch-2.35.yml          日後：補丁
├─ variant-私規.html       日後：私規變體
└─ notes.md                日後：修訂筆記
```

優點【觀察】：
- **撞名歸零**。同一標題（如「D級武器」）在科技本質／特異本質／魔幻本質各有一份，靠完整路徑自然區分。
- **路徑長度安全**。最長 124 字元，遠低於 Windows 260 上限。
- **網址即語意**。`/資源/血統/人類/特異本質/禍神血脈/` 自帶完整分類資訊。

### 沒有 `index.html` 的目錄

目錄存在但沒有 `index.html` 時，代表它是**純分類節點**：導航上看得到、可以展開，但不可點擊。這是刻意的設計，不是缺檔。

目前有 136 個這種節點。其中 24 個是因為移除了空佔位頁（見 §7.2）。

## 7. 變更紀錄

### 7.1 導航點擊會在瀏覽器彈出新視窗【已修】

**症狀**：點導航項目，內容在瀏覽器新視窗開啟，而不是在右側閱讀區。

**原因**：兩個 bug 疊加。

1. `script.js` 的 `isValidPage()` 只接受 `.htm` / `.html` 結尾的路徑。條目改成「資料夾 + index.html」後，網址形如 `資源/血統/人類/禍神血脈/`，被判定為「非本站頁面」，走進 `window.open()` 分支。
2. `dtree.js` 第 243 行把 `target="body"` 寫死在連結上。`body` 是舊 CHM frameset 的頁框名（`<FRAME name=body>`），新版入口網站沒有這個頁框，瀏覽器找不到就另開視窗。

**修正**：`isValidPage()` 接受目錄式網址並保留舊 `.htm` 相容性；`toPage()` 排除入口網站自身；`dtree.js` 移除 `target` 屬性。

**commit**：`0a179dd`

### 7.4 資源抽取器：分段批次執行【已建立】

把「全站一次抽完」改成「切成 57 段、每段獨立落盤」，避免中斷後整份作廢。

**為什麼需要分段**【觀察】

單頁抽取約 2.4ms（中位數 1.5ms、最慢 23.4ms），全站 1147 頁約 3 秒。真正的風險不是「跑太久被逾時砍斷」——3 秒遠不到任何逾時門檻——而是**中斷後已完成的工作全部作廢**，以及**某一段出錯時整批無法交付**。分段把「重做成本」從「全站」壓到「一段」（約 20 頁、0.04 秒）。

**分段方式**【觀察】

不依路徑順序連續切塊，而是**先按檔案大小降序、再 round-robin 分配**。連續切塊會讓大型分類（如 `資源/技藝/其他能力`）整段落在一起、耗時嚴重不均；round-robin 把大頁攤平到每一段。

| 項目 | 數值 |
|---|---|
| 段數 | 57 |
| 每段頁數 | 20–21 |
| 每段大小 | 395–647 KB |
| 單段最慢耗時 | 87ms |

**可靠機制**

| 機制 | 說明 |
|---|---|
| 原子寫入 | 段檔先寫 `.tmp` 再 `os.replace`，中斷不留半截 JSON |
| 續跑 | `run` 會跳過已完成且檔案存在的段；段檔遺失則自動重做該段 |
| 錯誤隔離 | 單頁解析失敗只記進 manifest，**不影響同段其他頁** |
| 可疑偵測 | 抽出後字元 < 20 的頁標記為可疑（見 §7.5） |
| manifest | `build/extract-parts/manifest.json` 記錄每段狀態、耗時、錯誤 |

**實測驗證**【觀察】

- 續跑：重跑已完成段 → 正確跳過
- 中斷復原：刪掉段檔但保留 manifest → 自動重做該段

### 7.5 發現一個先前未偵測到的空頁（已於 2026-10-22 刪除）

**位置**：`Resource/資源/物品/魔幻本質/智能神器/index.html`（358 bytes）

2026-10-22。三個缺口都已實作修正並通過回歸測試。**這是資料品質的關鍵轉折**——在此之前 `extract-all.json` 不可視為可用資料，修好後可以。

#### 缺口①　只認 `====` 分隔線 → 多條目塌成一條

**症狀**【觀察】原始 HTML 是 WinCHM 輸出的 `<P>` 段落序列。舊版只認 `====` 分隔線當條目邊界，但只有 166/1147 頁有分隔線，其餘頁面的多個條目全被塌成一個。`資源/稱號`（117 頁）、`資源/改造`（109 頁）、`資源/血統`（79 頁）最嚴重。

**修法**【決定】改為兩層切分，兩者併用：

| 層 | 訊號 | 說明 |
|---|---|---|
| 層 1 | `====` 分隔線 | 166 頁有，最可靠的邊界，優先 |
| 層 2 | 段落規則 | 其餘頁靠「名稱段 + 欄位組」隱含切分 |

段落規則的判準：

```
候選點  = 非欄位開頭的段落，且下一個非空段落是欄位開頭
條目起點 = 候選點，且下一欄位 ∈ {本質, 名稱, 稱號, 血統}
排除    = 等級標題（D級…）／「技能樹：開啓X級」／以標點開頭／長度 > 30
```

**為什麼要求「下一欄位是本質」**【觀察】資源條目一定帶本質（物品、血統、瞳術…）；而子項目只帶價格、不帶本質——例如魔杖的杖身「樺木」、喪屍的「力量型」分支、喪屍的「C級」等級。這個判準把「條目」和「子項目」分開了。

**驗證**【觀察】回歸測試涵蓋 6 個實地核對過的案例，全部通過：玲瓏骰 4 條、D級手槍系列 6 條、通用D級法術 65 條、C級武器 80 條（杖身子項目未被誤切）、寫輪眼 1 條、賽亞人 1 條。

#### 缺口②　同名字段只留第一個 → 85% 欄位蒸發

**症狀**【觀察】`split_fields` 遇到重複欄位名直接 `continue` 丟棄。64133 個欄位中有 55063 個（85%）因欄位名重複被丟——丟掉的是「效果」（1608 個）、「描述」（1280 個）、「價格」（973 個）等**第二個以後的值**。

**修法**【決定】第一個值留在 `fields[name]`（向後相容），所有值收進 `fields_multi[name]`（陣列）。不丟任何資料。

#### 缺口③　價格解析過嚴 → 11% 解析失敗

**症狀**【觀察】`parse_price` 用 `re.fullmatch`，但原文常見「D+500 強效施法：…」「C+1000 消耗：見下」這類寫法——價格只是欄位開頭的一小段。

**修法**【決定】改為取**開頭的價格 token**，其餘文字原樣放進 `price_note`；另加「總價」寫法（「特殊(總價D+2000)」）。無絕對數值者（「價格是原來的 50 倍」）仍回傳 `null` + 警告，**不硬猜**。

### 7.7 v4 抽取器：段落級重構【已修正】

2026-10-22。§7.6 修的是「修好 v3 的資料遺失」，但 v3 的架構本身有天花板：它以「欄位」為解析單位，遇到「等級本身的欄位」「段內混排」「整條目壓在一段」就會出錯。v4 改以**段落**為單位重寫。

#### 為什麼要重寫

| 問題 | v3 的表現 | 根因 |
|---|---|---|
| 等級自己的欄位 | 屬性/能量池/技能樹/特性/特殊 被塞進 `levels[].tree[]` 的能力裡 | 沒有「等級區塊」的概念 |
| 整條目壓在一個 `<P>` | DOTA 能力組 13 段 → 只抽到 0 條目 | 只認段落邊界，不認段內結構 |
| 續行段落 | 沒有標籤的續行文字被丟掉 | 只認「標籤：值」 |
| 欄位同名 | 陣列與單值並存，語意混雜 | 兩套機制同時維護 |

#### v4 的三層結構

```
條目 entry
├─ fields_multi        條目本身的欄位（本質、描述…）
├─ levels[]            等級
│   ├─ level           D / C / B / A / S
│   ├─ label           等級名（「骷髏兵」「初武・萬里長城平地起」）
│   ├─ fields_multi    等級自己的欄位（屬性、能量池、技能樹、特性、特殊）
│   └─ tree[]          該等級的技能樹能力
├─ abilities[]         不屬於任何等級的能力
└─ variants[]          子項目（帶 group 欄位）
```

**三個關鍵判準**【決定】

1. **等級區塊**：名稱段後接著 ≥2 個等級欄位，且其中至少一個是 {屬性, 能量池, 技能樹} → 該名稱是**等級**而非能力。
   覆蓋兩種排版：`(A)`「D 級骷髏兵」+「向前衝！炮灰！」+ 欄位（levels[] 直接掛欄位）；
   `(B)`「新兵」+ 散文 + 「D+600」獨立價格段 + 欄位（等級代號從價格段推得）。

2. **群組成員分類**：含施放型欄位（動作/效果/能耗/射程/目標…）或群組名含技能樹/異能/法術 → **能力**；
   只有價格加物品型欄位 → **變體**（子項目）。
   這一條把「血族異能說明：」底下的 33 個異能從「變體」還原成「能力」。

3. **段內切分**：一個 `<P>` 內混排多個「X 級：」或「欄位名：」時，在切點處拆成子段落。
   DOTA 能力組 13 段 → 402 段，全站覆蓋率 72.3% → 81.7%。

#### schema 決定（與維護者逐項確認過）

| 項目 | 決定 |
|---|---|
| 欄位容器 | **只用 `fields_multi`**（陣列），`fields` 整個移除——避免漏值 |
| 非 schema 標籤 | 進 `fields_extra_multi`，**保留原標籤**（如「強效施法」「化身骷髏」） |
| 續行段落 | 併入**前一欄位** |
| 無標籤散文 | 進 `notes` |
| 能量欄位 | 統一正規化為「**能量池**」 |
| 子項目 | 拆成 `variants[]`，`group` 記錄母群組，**與父項目同檔** |
| 變體層級 | `variants[]` 攤平在**條目頂層**（不巢狀） |

#### 欄位詞典 `build/field_schema.json`（已進版控）

欄位不是「看到標籤就建欄位」，而是依**跨資源使用範圍**分層【決定】：

| 層 | 判準 | 數量 | 處理 |
|---|---|---|---|
| `core` | ≥30 個頁面用到 | 54 | 正式欄位 |
| `extended` | 5–29 個頁面用到 | 63 | 人工篩選後的正式欄位 |
| 其他 | <5 個頁面用到 | 11626 | **不建欄位**，原標籤進 `fields_extra_multi` |

依此原則「強效施法」只出現在 2 頁 → 不建欄位；「屬性」「價格」上百頁 → 建欄位。

#### `fields_extra_multi` 長什麼樣子

全站 24,647 個值、9,937 個不重複標籤，分佈在 993/1147 頁。依使用頁數：

| 使用頁數 | 標籤數 | 性質 |
|---|---:|---|
| ≥30 頁 | 0 | 全部升格為正式欄位了 |
| 5–29 頁 | 149 | 接近門檻但仍不足 |
| 2–4 頁 | 863 | 單一資源專屬 |
| 1 頁 | 8,925 | 幾乎全是一次性標籤 |

**三種典型樣貌**【觀察】

**(1) 真正的並列分支** —— `資源/技藝/特殊武器/妙筆丹青` 的「丹青化五靈」底下有五個元素分支：

```json
"fields_extra_multi": {
  "風": ["進行風度 + 表達 - 丹青的檢定，造成成功點數的暈眩點數，強韌豁免。"],
  "水": ["進行風度 + 表達 - 丹青的檢定，造成成功點數的凍結點數，強韌豁免。"],
  "火": ["進行風度 + 表達 - 丹青的檢定，造成成功點數的燃燒點數，反射豁免。"],
  "雷": ["進行風度 + 表達 - 丹青的檢定，造成成功點數的麻痹點數，強韻豁免。"],
  "土": ["進行風度 + 表達 - 丹青的檢定，造成成功點數的糾纏點數，反射豁免。"]
}
```

這是**最好的一類**：原標籤保留、值完整、事實上是一組並列子項。之後若要正規化，可以把它們升格成 `variants[]`。

**(2) 技能名 + 數值** —— 技能清單類標籤，值其實是結構化數字：

```json
"意志": ["26"],
"調查": ["4"],
"肉搏": ["8 （擒抱 爪擊 噬咬）"],
"躲藏": ["4 （潛行，躲藏）"]
```

這些**不是欄位而是列舉值**（技能名），但值的形狀像欄位值。日後做資料庫時要區分開。

**(3) 解析誤判** —— 單字或純數字的「標籤」其實是句子開頭或條目名後接說明：

```json
"如": ["耐力11，受到6點噁心點數，則無視這6點噁心點數的影響……"],
"1": ["10 點經驗。 +1 意識"],
"2": ["20 點經驗。 +1 意識， +1 親和獲得主動技能：御氣飛行"]
```

量測【觀察】明顯誤判的標籤有 **154 個**、涉及 **828 個值**、分布在 **98 頁**（佔全站 8.5%）。
**沒有資料遺失**——值都原樣保留，只是歸類在 `fields_extra_multi` 而非正式欄位。

**結論**【決定】維護者指示「`extra_multi` 先保留」。目前的行為符合這項指示：原標籤、原值都完整保留，沒有丟失。日後逐項檢查時再決定哪些要升格成正式欄位、哪些要併進正文。

### 7.8 Markdown 資源書與條目名稱修正【2026-10-22】

#### 條目名稱：散文誤判

v4 初版把**段落**當條目名，有些頁面的第一段是引導散文而非名稱，導致名稱長得像句子。
修正後的判定順序（`extract_v4.py` 的 `pick_name()`）：

1. 第 0 段短、無冒號、不是散文 → 就是名稱（「無名劍法」「狂戰士」「第六質點，Tiphareth。美麗/平衡」）
2. 第 0 段是散文 → 往後找第一段短且無冒號的（「狂戰士」頁第 0 段是引導句，第 2 段才是名稱）
3. 第 0 段是「名稱：說明」型 → 拆出名稱，說明轉 `notes`（「第九質點：Yesod。基礎」）
4. 都找不到 → 用頁面路徑尾段當名稱

「散文」的判準是**含句讀且長度 > 16 字**——短句仍可能是名稱。

| 指標 | 修正前 | 修正後 |
|---|---|---|
| 完全沒內容的條目 | 47 | **0** |
| 名稱含句讀（散文型） | 155 | **84** |
| 名稱過長（> 24 字） | 119 | **54** |

剩下的 84 筆多數是**合法名稱**（`第三質點，Binah。理解`、`第六律者，死之律者`），不是錯誤。

#### Markdown 資源書 `build/export_md.py`

資源抽取（結構化資料）：

python build/extract_batch.py merge # 合併段檔 → build/extract-all.json
python build/extract_batch.py status # 顯示各段狀態

Markdown 資源書（可讀輸出）：

`export_md.py` 把 `build/extract-all.json` 轉成 Markdown。輸出目錄是 `build/md/`（**不進版控**，可隨時重建）。
目錄 `INDEX.md` 的順序與網站導航一致（讀 `Resource/left.htm`），不是字典序。

偶爾用到：

```

**歷史遷移腳本**，只支援特定階段的輸入狀態，不可重複執行：

```

**目前 repo 已在最終結構。** 要重跑遷移腳本請先 `git checkout <commit> -- Resource`。

### 版控注意

`build/original-order.json` **必須進版控**（已加 `.gitignore` 例外）。它是導航排序的依據，缺少它會導致各分類退回名稱排序。其餘 `build/*.json` 是暫存產物，不追蹤。

`build/extract-parts/`（段檔與 manifest）與 `build/extract-all.json` 同樣不追蹤——它們是 `extract_batch.py` 的可重建產物，體積大且不入版控。需要重跑時用 `plan` → `run` → `merge` 重建即可。

**`build/extract_batch.py` 本身要進版控**（它是工具，不是產物）。

## 10. 給 AI／協作者的使用說明

- **取得完整內容**：`git clone https://github.com/Sora0811/UnlimitedHorrorTrpg.git`。只能讀網頁的工具可能被 GitHub 頁面擋下（robots），公開網站的導航與內容位於 iframe 內，也不易被抓取。
- **原則**：不得以一般 RPG 的常見結構推論 UH 的結構；原文沒寫的就是【未知】；引用請附**完整路徑**（例如 `資源/血統/人類/特異本質/禍神血脈/`），標題會重複，不可單獨使用。
- **不要手改 `left.htm`**，改 `gen_nav_fs.py` 的 `ORDER` 或資料夾結構後重跑。
- **搬移條目後一定要跑 `gen_nav_fs.py`**，否則導航與檔案系統會不同步。
